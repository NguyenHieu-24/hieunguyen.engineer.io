THE PROBLEM

Why this project exists.

Collect product information from an API and convert inconsistent source responses into structured records for downstream use.

IMPLEMENTATION

What the implementation includes.

  • Separated loading, fetching, transformation, writing, monitoring, and checkpoint responsibilities.
  • Used concurrent HTTP requests with a connection limit and threaded transformations.
  • Recorded failed requests separately and saved progress after batch output.

main.py · pipelines/ · output/ · errors/

ARCHITECTURE

The data flow.

CSV product IDs→Async requests→Normalize fields→JSON batches

High-level illustration of the implemented workflow.

Modular stages

Separate responsibilities make individual stages easier to inspect and change.

Batch checkpoints

Progress is tracked by batch position. Resuming requires the same input order and batch size.

Error records

Failed requests retain their product ID, batch, error, and timestamp for investigation.

EVIDENCE

Results and scope.

These counts were calculated from the supplied archive. They are not a new pipeline run, a completeness guarantee, or a throughput benchmark. The archive contains 19,573 HTTP 429 errors and 933 HTTP 404 errors.

NEXT ITERATION

Limitations and improvements.

  • The current source logs failed requests but has no retry pass.
  • The configured input CSV is not included in the supplied archive.
  • Input validation, rate-aware backoff, and replay of failed IDs are next improvements.

REPRODUCE

Running the original project.

Provide the configured product-ID CSV, install the repository dependencies, and review the existing checkpoint before running python main.py. Preserve bundled output before using reset.
